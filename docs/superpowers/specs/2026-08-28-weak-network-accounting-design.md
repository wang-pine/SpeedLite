# 弱网测速对账设计

## 目标

让网页 TCP/WebRTC 测速在高延迟、低带宽和发送缓冲积压时使用一致的开始与结束边界，避免把尚未排空的数据计为已传输；同时使页面上的平均速率、峰值、交付损失和服务端对账具有明确且可验证的口径。

## 范围

本次修改覆盖：

- 网页 TCP（WebSocket）上行、下行、双向的结束协议与本地统计。
- 网页 UDP（WebRTC DataChannel）上行、下行、双向的尾部排空与对账语义。
- 多流结果的平均速率和峰值汇总。
- 服务端统计返回结构、页面文案、用户手册和自动化回归测试。

原生 `speedctl` 的 TCP/UDP 协议不变。网页 UDP 不宣称测得 IP 层 UDP 包丢失率；原生 `speedctl udp` 继续负责带序号的精确包丢失与抖动统计。

## 设计原则

1. 统计边界由协议事件确定，不由互不相关的客户端和服务端定时器分别猜测。
2. `send()`/`DataChannel.Send()` 成功只表示数据已提交；排队数据不能算作已经排空或已经交付。
3. TCP 的可靠有序语义用于建立精确结束边界；正常完成时两端应用负载字节应一致。
4. WebRTC 对账展示应用层交付损失，明确区分提交量、残留队列和对端接收量。
5. 汇总值必须与页面展示的总字节和用时满足同一个计算恒等式。

## TCP 协议

### 控制消息

WebSocket 文本消息使用以下类型：

- 服务端到浏览器 `{"type":"start"}`：该流已准备好，浏览器从此刻开始计时和打流。
- 浏览器到服务端 `{"type":"stop"}`：浏览器已停止调用 `send()`；此消息排在此前所有二进制帧之后。
- 服务端到浏览器 `{"type":"result","result":...}`：服务端已完成该流统计；此消息排在此前所有下行二进制帧之后。
- 服务端到浏览器 `{"type":"error","error":"..."}`：协议或传输失败。

### 上行

浏览器收到 `start` 后开始发送。测试时长到达时停止产生新数据，然后在同一 WebSocket 上发送 `stop`。WebSocket/TCP 的有序性保证服务端读到 `stop` 前已经读到此前所有二进制帧。服务端以读到 `stop` 的时刻结束统计并返回 result。

浏览器正常完成时的上行总字节使用 `sentTotal`，因为 result 只有在服务端读到排在数据后的 `stop` 后才会返回。如果连接在 result 前断开，则结果标记为失败，不把 `sentTotal` 当作已交付量。

### 下行

服务端从发送 `start` 后开始计时，持续写二进制帧至指定时长，然后在同一 WebSocket 上写 result。浏览器只在收到 result 时生成最终结果；由于消息有序，此前所有下行帧已经触发浏览器的 `message` 事件。

浏览器本地定时器只承担“服务端失联”的看门狗职责，不能生成成功结果。

### 双向

上行沿用浏览器 `stop` 边界，下行沿用服务端时长边界。服务端等待“下行发送完成”和“上行读到 stop”两个条件均满足后返回一个合并 result。任何一侧异常都使该流失败，不生成貌似成功的部分对账。

### 超时

每个流设置 `测试时长 + 10 秒` 的完成看门狗。超时返回明确错误并关闭连接。看门狗只负责失败退出，不参与正常统计边界。

## WebRTC DataChannel 协议

WebRTC unreliable DataChannel 无法提供 TCP 式交付确认。因此页面保留双端统计，但调整术语和完成顺序。

### 上行

浏览器在 DataChannel `open` 后开始计时。测试时长到达时停止产生新消息，但保持 DataChannel 和信令 WebSocket 打开。浏览器持续观察 `bufferedAmount`，直到降为 0 或达到 3 秒排空上限，然后通过信令 WebSocket发送 `{"type":"stop","queued_bytes":N}`。

服务端收到 stop 后再等待 800 ms 的在途数据宽限期，随后返回接收字节数。浏览器侧“已排空量”为 `sentTotal - queuedBytes`；残留量单独展示。若仍有残留，结果标记为截断，不能把残留当作网络丢包。

### 下行

服务端在 DataChannel `open` 后开始计时。时长到达时停止调用 `Send()`，等待 DataChannel `BufferedAmount()` 降为 0 或达到 3 秒排空上限，再通过信令返回：

- `total_bytes`：已从服务端 DataChannel 发送队列排空的应用负载字节。
- `submitted_bytes`：调用 `Send()` 成功的应用负载字节。
- `queued_bytes`：结束时仍在队列中的应用负载字节。

浏览器保持 DataChannel 打开直至收到 result，确保排空阶段到达的数据进入本地接收统计。

### 双向

两个方向分别执行上述停止和排空过程。result 返回方向拆分字段，页面分别展示上行与下行的排空量、接收量和残留量；合计字段仅用于结果表总览。

### 交付损失定义

网页 UDP 的指标名称改为“交付损失”，而不是“丢包率”：

- 下行：`max(0, 服务端已排空字节 - 浏览器接收字节) / 服务端已排空字节`。
- 上行：`max(0, 浏览器已排空字节 - 服务端接收字节) / 浏览器已排空字节`。
- 排队残留不进入交付损失分子或分母，单独标记为“队列截断”。

该值表示 WebRTC 应用层消息的交付差额，可能包含 SCTP/DTLS/UDP 路径上的丢弃，不能解释为 IP 层 UDP 包丢失率。精确包丢失率和抖动继续由 `speedctl udp` 提供。

## 统计结构

扩展 `engine.Stats`：

- `SubmittedBytes uint64` / `submitted_bytes`：成功提交给发送 API 的应用负载字节。
- `QueuedBytes uint64` / `queued_bytes`：完成时仍在发送队列中的应用负载字节。
- `UpBytes uint64` / `up_bytes`：服务端收到的上行应用负载字节。
- `DownBytes uint64` / `down_bytes`：服务端已排空的下行应用负载字节。
- `Truncated bool` / `truncated`：排空超时或异常结束导致结果截断。

保留 `total_bytes` 兼容现有页面和 CLI；网页单向时取对应方向的可对账字节，双向时取 `up_bytes + down_bytes`。

## 浏览器统计模块

将纯计算从传输流程中抽出，作为 `window.__speedTestCore` 可测试接口：

- `drainedBytes(submitted, queued)`：返回非负的已排空字节。
- `makeStreamResult(...)`：以明确的开始/结束时间和方向字节生成单流结果。
- `aggregate(results, dir)`：按汇总字节和统一用时生成最终平均值与对账信息。

`makeMeter()` 只负责累计字节和同步窗口采样；传输流程不再在完成时调用 `syncTX(sentTotal)` 覆盖校正值。

## 平均值和峰值

### 平均值

一次多流测试记录统一的阶段开始、结束时间。最终平均速率为：

`汇总可对账字节 × 8 / 阶段实际秒数 / 1,000,000`

因此“总传输、用时、平均速率”始终自洽。双向结果分别用上行字节和下行字节除以相同阶段用时。

### 峰值

每 100 ms 对所有活跃流先采样，再按方向求和，将聚合采样保存在近 1 秒的时间窗口中。峰值取聚合窗口速率的最大值。禁止累加各流在不同时刻取得的独立峰值。

服务端峰值仍作为独立诊断数据，但页面文案注明其采样窗口；对账等级只按字节计算，不按峰值计算。

## 页面表现

- TCP：正常完成且字节偏差小于 1% 显示“对账正常”；大于等于 1% 标记为协议/截断异常。
- UDP：显示“交付损失”，并在明细行展示提交、排空、接收、残留。
- `queued_bytes > 0` 或 `truncated=true` 时显示“队列截断”，该次结果不作为链路丢包结论。
- 服务端统计未返回时整条流失败，不再以缺少对账数据的本地估计保存为成功历史。
- 抖动继续显示不可用提示，不能显示具有精确含义的 `0.0 ms`。

## 错误处理

- WebSocket/DataChannel 在 result 前关闭：流失败，保留错误原因，不产生成功统计。
- 部分并行流失败：整次链路测试标记为不完整，页面列出成功流数与失败流数；不把成功流伪装成配置的完整并行测试。
- 排空超时：返回可用的已排空/已接收数据，同时设置 `truncated=true`，页面警示该结果仅供参考。
- 用户主动停止：关闭所有连接，不写入历史结果。

## 测试策略

### 前端纯逻辑测试

使用 Node 内置 `node:test` 和 `vm` 加载真实 `app.js`，不新增 npm 依赖。覆盖：

- 10 MiB 提交、6.37 MiB 排队时，只计 3.63 MiB 已排空。
- 多流平均值满足 `总字节 / 汇总用时`，不累加各流独立平均值。
- UDP 交付损失排除队列残留。
- 偏差范围为 0–100%，TCP 1% 阈值和 UDP 截断文案正确。

### Go 单元与集成测试

- `engine.Stats` JSON 字段及方向合并。
- WebSocket 上行：客户端发送二进制帧后发送 stop，result 的字节数精确相等。
- WebSocket 下行：result 一定排在全部二进制帧之后。
- WebSocket result 前断链：不能生成成功结果。
- WebRTC 排空计算：submitted、queued、total 三者满足 `total = submitted - queued`，且不会下溢。

### 弱网验收

在 Linux `tc netem` 环境分别施加低带宽、高延迟和丢包，运行 4 流 10 秒：

- TCP 上/下行正常完成时，浏览器与服务端应用字节偏差小于 1%。
- TCP 页面平均值与总字节/用时计算偏差小于 0.1%。
- UDP 队列残留被单独报告，不进入交付损失。
- UDP 无残留时，交付损失与两端可对账字节计算完全一致。
- 所有模式均不会出现超过 100% 的偏差或损失。

## 兼容性与部署

网页前端与服务端由同一 Go 二进制内嵌交付，因此 WebSocket/WebRTC 控制协议同步升级，不提供跨版本网页与服务端兼容保证。部署后必须强制刷新浏览器缓存。原生 `speedctl` 协议保持兼容。
